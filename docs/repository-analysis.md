# Repository AI code analysis

`complyscan scan` uses a hybrid analysis pipeline when `ai.review-on-scan: true` is backed by matching private trust recorded by guided setup on this machine, or when provider options supply explicit one-run consent. Local deterministic code always runs first: it discovers the repository, inventories AI signals, maps technical-objective matches, identifies production entry points, and builds a code graph. The model then receives one or more bounded evidence packages built from those anchors and their connected code. Trust binds provider, endpoint, model, and credential environment-variable name; repository intent alone cannot authorize a clone, changed identity, or ephemeral runner. `complyscan scan --deterministic-only` stops after the local layer and never reads a provider credential or contacts a model. Legacy or untrusted configurations retain deterministic scan behavior and print migration or trust guidance.

## Default pipeline

1. ComplyScan loads its active configuration and optional `.complyscan/ai-uses.yml` register locally, then excludes both exact files from discovery and model context.
2. Discovery applies the existing `.gitignore`, exclusion, size, count, binary, symlink, dependency-directory, generated-output, and nested-repository boundaries.
3. Local code classifies files, redacts recognised credential formats, inventories likely AI integrations, applies technical evidence rules, and builds the Go, Python, JavaScript, and TypeScript repository graph.
4. The selector ranks implementation files using AI inventory signals, technical-objective matches, production entry points, imports, callers, bounded graph relationships, and active confirmed AI-use paths. Documentation is not used as the primary proof of an implementation.
5. The selector prepares one bounded excerpt for every structural candidate file. If all excerpts and their trimmed graph context fit the per-request boundary, the provider receives one structured request. Otherwise ComplyScan partitions the complete candidate queue into bounded source batches, reviews every batch, and synthesizes their validated summaries. Each confirmed-use context carries its stable human-owned ID, descriptive scope, associated configured systems, files submitted in that request, and only the likely-required or recommended objectives screened for that use and system. The response contract also permits positive typed repository facts keyed to an exact returned candidate or supplied confirmed-use ID.
6. A single-package targeted review may request one follow-up containing at most three literal search terms and optional repository-relative path hints. Trusted local code—not the model—searches only eligible discovered files and returns at most three bounded excerpts. If useful excerpts are found, ComplyScan makes one final structured request. If that initial response instead exhausts its output allowance, ComplyScan uses the same sole second-call budget for a terse no-follow-up recovery. Multi-batch targeted review uses the bounded batch-and-synthesis path rather than a follow-up round.
7. Trusted code validates objective IDs, configured system IDs, transient model-suggestion IDs, supplied confirmed-use IDs, use/objective/system combinations, typed fact fields and values, paths, line citations, and ownership boundaries. Every requested confirmed-use combination must receive one direct observation. A definite direct decision and every returned fact need checked citations from files submitted for that use. Missing combinations, unknown or fuzzy AI-use bindings, absence-based negative facts, or invalid output reject the model pass. Suggestion IDs bind one model response only and never become durable project identity; a direct objective observation instead preserves the stable human-owned ID that ComplyScan supplied.
8. Local code overlays those model facts with full-repository deterministic provider references. It does not turn an import or endpoint into an inference claim; a scoped local command or installer becomes a `local-cli` fact only after positive AI activity is supported. It may derive conditional `possible` provider, downstream-provider, or deployer candidates from bounded integration and distribution evidence, but never a statutory role.
9. The advisory result is saved separately from deterministic findings and does not change the scan's CI threshold, profile, applicability, or human-owned AI-use register.

The normal trusted or explicitly requested AI path therefore uses one request when the structural candidate queue fits the provider boundary, or as many bounded source batches and synthesis requests as the queue requires. The batching unit is one selected candidate file excerpt—not one request per invocation path, directory, objective, or confirmed AI use. A completed zero-use result is possible only after every selected candidate batch has completed. If a provider, validation, or cancellation error stops batch `N` of `M`, ComplyScan preserves attempted-transfer and completed-batch coverage but discards unsynthesized semantic conclusions, labels the AI layer incomplete, and reports how many batches finished; it never converts partial coverage into a completed zero-use result. `--require-ai-review` can make that state return exit code `2` after report artifacts are written, but never grants consent by itself.

## Pull-request review scope

`complyscan scan --changed-since <git-ref>` keeps the repository-wide governance layer local while narrowing every source-bearing model request to the change. ComplyScan includes every changed model-eligible source, manifest, configuration, CI, container, infrastructure, or environment-template file. It then uses the complete repository graph locally to add at most eight unchanged source files connected within two call, route, authorization, persistence, logging, configuration, test, or import hops. Unrelated files are never added merely because they contain an AI or compliance keyword.

The same in-memory changed-plus-connected repository is the hard boundary for targeted selection, broad review modes, per-objective technical investigations, eligible-file manifests, and model-requested follow-up searches. Targeted batching exhausts structural candidates only inside that scoped set. Consequently, choosing `deep`, `full`, or `hierarchical` together with `--changed-since` can broaden analysis only inside that bounded change context; it cannot restore whole-repository model access. Deterministic inventory, framework evidence, reconciliation, documentation checks, and risk-file checks still use the complete local snapshot as documented by their own scan scopes.

Terminal, Markdown, and JSON coverage distinguish the full locally checked repository from the model boundary. They record the `changed-plus-connected` review scope, changed files included, connected files included, files available to local context selection, and excerpts actually submitted. Deterministic per-use facts still use the complete discovered repository and carry `full-repository` coverage; model-reasoned facts carry `changed-plus-connected` coverage. Files outside that model boundary were not reviewed by the model, so an absent model observation is never evidence that an unchanged implementation is missing.

The saved AI-use register remains repository-wide human-owned state during this scoped run. A confirmed use receives direct review context only for files where its human-owned path scope intersects the changed-plus-connected boundary; a use with no submitted file receives no use-specific model context. ComplyScan may overlay changed technical observations and suggestions, but a missing observation from changed-plus-connected context cannot delete or retire a saved use.

The composite GitHub Action defaults to `scope: auto`. It obtains the base SHA on `pull_request` events and applies this changed-plus-connected boundary there; ordinary non-PR events use the full repository. `actions/checkout` should use `fetch-depth: 0`. If a normal pull request's base is missing or unavailable locally, the Action fails instead of silently falling back to a full model scope. Change-scoped `pull_request_target` runs are refused because their default checkout is the base branch; use `pull_request` for change scanning, or consciously choose `scope: full` only for an intended base-branch scan. The Action separately defaults `ai-review: none`, which forces deterministic-only operation; `configured` or a provider value is explicit one-run consent, and `require-ai-review` alone cannot activate a provider. `scope: pull-request` requires a usable base, and `scope: full` is the deliberate whole-repository choice.

## Modes

Configure the strategy under `ai.repository-analysis`:

```yaml
ai:
  repository-analysis:
    mode: auto
    max-input-tokens: 180000
```

- `auto` is the recommended default and currently selects targeted evidence.
- `targeted` explicitly selects the same targeted-evidence strategy as `auto`.
- `deep` enables the previous broad strategy: one full request when it fits, otherwise hierarchical subsystem analysis and synthesis.
- `full` requires one broad request and reports an incomplete model layer when the configured budget is too small.
- `hierarchical` always analyzes broad subsystem slices and synthesizes them.
- `bounded-only` disables repository-level analysis and retains the older per-candidate technical investigation flow.

`max-input-tokens` remains the upper safety budget for broad modes. Targeted remote analysis additionally aims for about 6,500 input tokens per request. This is a provider-request safety boundary, not a repository-wide evidence cap: additional structural candidate excerpts create additional source batches. For OpenAI GPT-5.6, both an initial targeted request and any recovery use medium reasoning effort with low text verbosity. The initial 4,096-token output allowance is a bootstrap value, not the model maximum: ComplyScan cannot know an account's token-per-minute ceiling before a response arrives. An intrinsically oversized request first retries with a smaller response allowance derived from the returned token ceiling. Single-package output recovery may then use `min(128000, returned token ceiling - actual input tokens)`; batched source and synthesis recovery grows only to 8,192 output tokens before splitting the context further. If OpenAI does not return a usable ceiling, ComplyScan keeps the bounded allowance rather than risk a guaranteed oversized retry. Experimental Ollama analysis uses a larger per-request package because no source leaves the machine. Input budgets are conservative estimates, not exact provider tokenization or billing guarantees.

The JSON evidence bundle records the actual mode as `targeted-evidence`, `full-repository`, or `hierarchical-synthesis`, together with discovered and submitted coverage, checked citations, token usage where supplied, and whether a bounded follow-up was used.

## What is sent by default

Targeted analysis may send selected excerpts from source code, dependency manifests, configuration, CI, GitHub Actions, Docker, Terraform, and environment templates. Selection is grounded in scanner matches and code structure. Every structural candidate file contributes one bounded excerpt to the queue, but this is not the same as sending every eligible repository file or independently enumerating every invocation path inside a file. A file that does not become a structural candidate is coverage debt, never evidence that an implementation is absent.

The raw active ComplyScan configuration—normally `.complyscan.yml`, or the exact file passed with `--config`—and the human-owned `.complyscan/ai-uses.yml` register are never part of the discovered snapshot or a model request. ComplyScan separately constructs typed system facts from the configuration. When the configured AI layer runs, it also derives bounded confirmed-use contexts locally: stable ID, name and description, saved path scope, valid configured-system associations, the exact selected files inside that scope, and likely-required or recommended objective contexts. The raw YAML, review history, dismissal records, and unrelated manifest fields are not sent. Other YAML files, including `.github/workflows/*.yml`, remain eligible because they can implement CI, permissions, tests, deployment, or safeguards.

Generated outputs, dependency trees, build directories, caches, binaries, symlinks, ignored paths, nested repositories unless explicitly enabled, files over the discovery limit, and credentials matching maintained secret patterns are not sent. Secret redaction is defence in depth, not a guarantee that arbitrary proprietary or personal data has been removed. A hosted provider remains an external source-code processing boundary.

The explicit `deep`, `full`, and `hierarchical` modes can send substantially more eligible repository text. Use them only when the extra coverage, provider limits, cost, and organisation policy have been considered.

## Rate limits and retries

Bounded targeted source batches and output schemas are intended to fit ordinary provider limits without silently discarding later candidates. Targeted responses cap AI uses, objective observations, unmapped activity, citations, unresolved questions, and individual text fields. Reports and JSON distinguish input, total output, and reasoning tokens where the provider supplies that breakdown. If a hosted provider still reports a temporary rolling rate limit, ComplyScan honours the provider interval, waits at least one minute, shows a cancellable countdown, and retries within the existing per-request cumulative wait budget. Oversized batches can be split further; the queue does not become an unbounded directory sweep because only structural candidate excerpts are included.

Deep modes retain adaptive splitting, incomplete-response recovery, hierarchical synthesis, and rate-limit waiting. These modes can require many requests and should not be the normal developer workflow.

## What the result means

The raw technical inventory reports integrations and signals. A model AI-use entry is a transient grouping suggestion supported by submitted repository citations. A developer-confirmed AI use is a human-owned grouping in `.complyscan/ai-uses.yml`; confirmation means that the named paths belong together as a product use, not that the use is legally classified or compliant. An objective observation says how strongly the submitted evidence supports a code objective. An unmapped observation records detected AI activity that does not fit a supplied objective. A repository fact is a narrower positive observation about one exact use, with explicit source, evidence strength, coverage, confidence, rationale, and checked citations. None establishes legal applicability, an organisation's statutory role, actual deployment, complete runtime behaviour, human practice, operational effectiveness, or compliance.

A configured AI layer records suggestions and observations in schema-version 12 reports but never writes the register. Version 12 records each inferred candidate's exact `member_observation_ids`; its `inferred-use-*` ID is generated locally from that sorted membership rather than from model wording. Version 11 added completed and total source-batch counters, while version 10 introduced nested repository facts, role candidates, and repository-invisible organisation context. Version 9's optional direct observation binding remains reserved for a supplied stable confirmed use. The report remains useful without a register. Developers who want durable cross-run naming can optionally use `complyscan ai-uses setup` or the dashboard; ordinary scans require no confirmation.

Deterministic observations currently preserve concrete runtime model-provider references inside each use's path scope. They deliberately do not infer an AI activity from an import, dependency, endpoint, or environment-variable reference. The optional model can reason across submitted callers, routes, data flow, tests, configuration, and deployment artifacts to add supported fields from the bounded fact taxonomy. A scoped command or installer is reported as `local-cli` only when the same use also has positive AI-activity evidence. The model must omit unknown, negative, absence-derived, actual-production, and retired claims. A checked citation proves the referenced submitted path and line exist; it does not prove operational effectiveness.

Role candidates are deliberately conditional. A runtime third-party provider connection may support a `possible` deployer candidate; an AI implementation plus executable release or installation artifacts may support a `possible` provider candidate; packaging that integrates a third-party model may also support a `possible` downstream-provider candidate. The report names the missing organisation facts for each candidate. Contracts, customer relationships, operating regions, actual professional or production use, product control, market placement, and the name or trademark used remain report-only unknowns. They do not create developer setup tasks, profile values, applicability outcomes, requirement mappings, or CI blocks.

Every active confirmed use also receives a deterministic `ai_use_mappings` result. Objective matches are filtered to the use's human-owned path patterns, then screened independently under every associated configured system. Matches found only outside that scope are retained as `evidence_outside_use`, allowing a developer to identify shared implementation or correct an incomplete path scope without counting it as evidence for the use. No or stale association preserves the code result but leaves legal and other context-dependent applicability unresolved; framework-wide voluntary practices may remain recommendations.

When the configured AI layer runs, those deterministic mappings define the likely-required and recommended use/objective/system combinations submitted to the model. One direct returned observation is required for each combination and is keyed by the supplied stable use ID, objective ID, and system ID. Definite decisions must cite only that use's submitted files; an uncited direct result may be retained only as uncertain. It can remain use-specific when two confirmed uses intentionally share code because the stable ID identifies the exact evaluation requested. A generic observation without a confirmed-use ID still attaches only when its citations identify one unambiguous confirmed use. Uncited repository-wide conclusions, invalid bindings, out-of-scope citations, and ambiguous generic observations remain repository-level. No scan mutates the register or lets model results change the failure threshold.

No AI use identified is not proof that a repository has no AI. `not_supported` is not proof that a mechanism is absent. A checked citation proves only that the referenced discovered path and line exist; a reviewer must still decide whether the model's interpretation is correct.

## Current limitations

- Targeted selection can miss implementations that produce no inventory signal, objective match, production-entrypoint relationship, or supported graph relationship.
- Static graph coverage is strongest for Go, Python, JavaScript, and TypeScript and remains incomplete for dynamic dispatch, runtime registration, metaprogramming, and other languages.
- Repository analysis is advisory and is not merged into deterministic CI failure thresholds.
- Source batches produce locally namespaced evidence observations, not durable use identities. Synthesis may merge connected observations across batches and must assign every observation exactly once, while previously validated groups cannot be split. Shared gateways and generic infrastructure can still leave identity ambiguous; ambiguity remains visible instead of forcing a merge.
- Multi-batch targeted review caches only the completed synthesized repository result. It does not yet persist or resume individual completed batches, so an interrupted run restarts the candidate queue.
- One model request accepts at most 500 direct confirmed-use/objective/system contexts. A larger review fails before that model request instead of silently dropping combinations; use a change-focused scope while partitioning those confirmed-use contexts across requests remains future work. This is separate from the implemented source-file batching.
- Completed repository results are reused only for an exact private-cache identity covering active review-scope content, framework evidence, profiles, ownership, derived confirmed-use IDs/path scopes/system-objective bindings, provider endpoint, model, prompt contract, context strategy, and token budget. Repository-analysis prompt version 10, private cache schema 4, and repository-analysis context version 5 bind request-specific objective/system/confirmed-use enums, the typed fact contract, trusted observation membership, locally derived inferred-use IDs, exhaustive targeted review, and exact member-scoped synthesis citations. A full scan binds the full discovered repository; `scan --changed-since` binds the changed-plus-connected model scope defined above. Any changed identity input causes a new request; `--refresh-review` always bypasses reuse.
- Context size and cost depend on the selected provider, model, and repository. ComplyScan records usage supplied by the provider but does not estimate price because provider prices change independently of the CLI.
