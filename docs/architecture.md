# Architecture

ComplyScan exposes one normal scan workflow with a mandatory local deterministic layer and a separately consented advisory AI layer:

```text
target directory
  ├─ selected, versioned technical evidence packs
  │    → legislation-specific applicability or voluntary recommendations
  ├─ validated, version-controlled system profiles
  │    → provisional EU applicability and high-risk screening where selected
  │    → activity- and deployment-sensitive objective screening
  ├─ validated path-to-system ownership rules
  │    → dedicated, intentionally shared, conflicting, or unassigned paths
  ├─ human-owned `.complyscan/ai-uses.yml` register
  │    → stable developer-confirmed groupings over current repository observations
  └─ bounded repository discovery and file classification
       → language-neutral relationship graph and technical-objective matching
       → typed AI provider and framework inventory
       → independently registered deterministic rules and findings
  → deterministic reconciliation per selected framework
       → legal-readiness mappings or voluntary recommendations
       → mapped candidate evidence, non-detections, mismatches, and unresolved ownership
  → conservative policy gate and preliminary local scan report
       → high-severity gap only for a human-reviewed, likely-required objective without detected evidence

configured `complyscan scan` when repository intent has matching private machine trust
	  → advisory local-Ollama or BYOK-provider model layers
	       → every structural candidate-file excerpt queued across bounded requests
		       → provider-aware concurrent source waves, then concurrent independent groups within each synthesis level
		       → finite schema repair and recursive splitting before an incomplete outcome; one semantic follow-up only for a single-package review
	       → broad full or hierarchical analysis only in explicit deep modes
	       → bounded finding review; per-objective investigation retained as fallback
  → terminal output plus atomic Markdown and schema-version 14 JSON reports, or SARIF

`complyscan scan --deterministic-only`
  → stops after the local layer without reading a provider credential or contacting a model
```

Installation and onboarding are a separate pre-scan path: the POSIX installer selects and verifies a release archive, then invokes `complyscan setup` only in a terminal. Interactive setup performs local discovery before establishing any optional model boundary. With consent, a configured model may prepare editable profile suggestions before the operator confirms facts that source code cannot establish. Selecting a provider saves repository intent as `ai.review-on-scan: true` and matching private trust outside the repository on that machine; setup then offers the unified scan or saving configuration only. The trust identity binds the provider, endpoint, model, and credential environment-variable name. Repository clones, changed identities, and ephemeral runners therefore remain deterministic until local setup or explicit one-run options authorize processing. Private recovery checkpoints store configuration fields—not repository source or credential values—in the operating-system user cache and are removed after save. External provisioning such as installing Ollama or pulling weights remains behind separate confirmation and never occurs during a normal scan.

`internal/reviewconsent` stores automatic-review approval beneath the operating system's per-user cache in `complyscan/review-consent`. The identity binds canonical repository and configuration paths plus a SHA-256 digest over provider, effective endpoint, model, credential environment-variable name, provider label, repository-analysis strategy and token budget, timeout, finding limit, and the current `adaptive-provider-pipeline-v3` context contract. That contract covers provider-neutral concurrency, larger adaptive hosted evidence packages, and the possibility that schema repairs or transient retries resend bounded source. Records contain the identity and consent timestamp, never a credential value or source. Directories and files require `0700` and `0600` permissions respectively, symlinks and non-regular paths are refused, reads are schema- and size-bounded, and writes are atomic. A check does not create state. Setup grants an exact match or revokes the repository/configuration record when AI is disabled.

`internal/modelqualification` separates automatic compatibility from maintained quality validation. It sends a source-free synthetic finding-binding request and then a minimal repository-shaped request containing only a fake one-line file and confirmed-use binding. Typed temporary capacity, transport, and provider failures share a four-request total ceiling inside the existing qualification timeout; the failed phase alone is retried. Permanent quota, request-size, cancellation, and contract failures return immediately, while usage and request accounting is retained. A successful result is cached privately for 30 days against the provider, exact model, available Ollama digest, qualification contract version 2, and all model prompt-contract versions, including repository-analysis prompt version 15 and setup-draft prompt version 6. Cache schema 4 uses `model-qualification-v4.json`; older finding-only results cannot be reused. Interactive setup runs or reuses this check automatically; non-interactive setup requires `--qualify-model`. A scan qualifies an unseen active model before repository context is sent. Failure is not cached and disables only that model layer, leaving deterministic reports intact. Compatibility never means benchmark validation, model quality, compliance, or legal approval.

`internal/discovery` owns filesystem traversal and file classification. It returns repository-relative slash-separated paths so findings are stable across macOS, Linux, and Windows. It skips nested repositories by default and supports Git-tracked-only scans, progress callbacks, and explicit scan budgets.

`internal/profile` owns declared system context, human review attribution, and conservative applicability screening. A repository may contain multiple systems. Controlled values make unknown context and spelling errors visible, while factual free-text labels are bounded. Explicit AI activities distinguish inference, training, fine-tuning, evaluation, automated decisions, agent tool use, and synthetic-content generation. Automated EU AI Act scope and possible high-risk signals are reported separately from human decisions and never produce a compliance verdict. Ordinary setup creates one draft report target from the repository name and leaves organisation-only context unknown; it asks only for the AI/provider/model choice, technical mappings, and the final save/run action. Code-visible facts are scan-owned report observations rather than setup answers. Advanced setup and `profile setup` retain the complete human-reviewed profile workflow for compliance owners and a future dashboard. Before every advanced-profile prompt, a centrally tested guidance catalog explains the requested fact and gives practical examples. Profiles created before the activity field was introduced remain valid but produce missing-context results until updated.

`internal/aiuse` owns the optional strict version-1 `.complyscan/ai-uses.yml` register and its report overlay. The source-controlled manifest contains developer-confirmed or draft product-use groupings, stable locally generated IDs, repository path patterns, optional configured-system associations, lifecycle state, human review attribution, and exact fingerprints for suggestions a developer explicitly linked; it contains no legal applicability or compliance conclusion. Scans load it locally and never mutate it. Repository-analysis suggestions remain useful transient report data without confirmation; a developer may optionally run `complyscan ai-uses setup` to improve per-use precision by confirming a new grouping, merging it into a saved grouping, recording a dismissal, or leaving it undecided. `complyscan ai-uses edit` is the separate guided mutation boundary for an existing saved use; it preserves stable identity and suggestion links while changing user-owned metadata, scope, associations, lifecycle, or review attribution without scanning or contacting a model. Model-authored suggestion IDs are not durable identity, and path overlap alone never establishes that two AI uses are the same. Conservative fingerprints may cause a materially paraphrased or relocated suggestion to be presented again instead of silently merging it. The exact manifest is excluded from discovery and raw model context. Changed-since observations are an overlay only, so a saved use outside the scoped evidence cannot be deleted or retired by omission.

The same package builds a scan-owned `repository_facts` overlay for each exact saved or current candidate ID. Deterministic full-repository signals preserve scoped runtime provider references without treating an import, endpoint, or setting as proof of inference. Checked model facts can add only positive values from the bounded code-fact taxonomy and retain their model coverage boundary; a scoped local command or installer becomes a `local-cli` fact only after AI activity is positively supported. The overlay also derives explicitly conditional `possible` provider, downstream-provider, and deployer role candidates from bounded integration and distribution evidence. It never writes a profile or manifest, changes applicability or per-use requirement mapping, or affects a gate. Repository-invisible organisation context is kept in `organization_unknowns` for the report only; it does not become a setup task or CI block.

`internal/framework` owns the embedded technical-pack schema, strict parsing, content digest, canonical control IDs, code-evidence matcher, and objective-specific reports. The CLI packs contain only objectives that inspect source, configuration, tests, CI, containers, dependency declarations, or infrastructure. Each objective records a source reference, the source's nature (`legislation` or `voluntary-framework`), and validated applicability conditions: `scope`, `activities-any-of`, and `external-use-required`. Multiple sources can map to one canonical control, so the same repository mechanism keeps one evidence fingerprint while each framework retains its own citation and interpretation. The built-ins are EU AI Act technical evidence and NIST AI RMF technical evidence. Packs do not activate legal controls, inspect uploaded documents, or roll objectives into a compliance status. The matcher requires an eligible file kind, a configured path signal, and every grouped content signal. Matches are `candidate-evidence`; an unmatched check is `not-detected`, never proof that an implementation is missing. Definition files can carry the narrow `complyscan:ignore-technical-evidence` marker to avoid self-identification. Pack content changes require a new version and digest.

`internal/codegraph` owns a language-neutral symbol, import, edge, and reachability model. Go is parsed with the standard library. The dependency-free Python indexer conservatively recognizes indentation-bounded functions, classes, methods, imports, calls, `__main__` entry points, tests, FastAPI and Flask decorators, Django route registrations, dependency-based authorization, configuration access, persistence, and audit/logging calls. The dependency-free JavaScript and TypeScript indexer recognizes functions, arrows, classes, methods, interfaces/types, ESM and CommonJS imports, calls, top-level entry calls, test callbacks, Express/Fastify registrations, Next.js route exports, NestJS decorators and guards, environment access, persistence, and logging. Comments, strings, and template literals are masked before structural extraction. Production entry points and test entry points are traversed separately so test-only or unreached candidates remain visible. Each technical match receives a maximum two-hop context package with report-safe symbol metadata, imports, relationships, and unresolved questions. Source excerpts remain in unexported graph state and cannot enter graph JSON. Unsupported or unparseable source remains visible as incomplete coverage and causes unmatched source objectives to be `not-evaluated`.

`internal/repositoryanalysis` prepares model context after deterministic inventory, technical-evidence matching, per-use reconciliation, and graph construction. Its default targeted path ranks AI signals, objective matches, production entry points, imports, callers, bounded graph neighbours, and active confirmed-use paths, then prepares one redacted excerpt for every structural candidate file. The raw manifest is never sent. Repository-analysis prompt version 15 treats source-batch candidates as evidence observations: independent source calls use sparse extraction, request lower reasoning effort where supported, and omit routine off-topic or merely uncertain objective rows. Orchestration replaces the model's temporary key with a scan-local identity derived from checked citation locations and batch position. Synthesis receives a compact grouping view with trusted member IDs, short semantic hints, and scan-local gap IDs. The model partitions every observation exactly once, may merge connected groups, and cannot split a previously validated group; it does not repeat facts or objective records. It may resolve a batch-local gap only through another member in the same group and a supplied checked citation. Local code validates the claim, group membership, and resolver citation, derives the final `inferred-use-*` ID from sorted membership, removes only those answered gaps, and reattaches the complete validated source records without imposing a single response's fact-value cap on the aggregate. Supplied confirmed-use IDs remain stable and separate. Typed positive facts remain citation-bound, while unsupported, negative, absence-derived, actual-production, and retired claims are forbidden. Hosted raw-source batches normally aim for approximately 24,000 input tokens per request, subject to a lower configured or observed provider boundary; this is not a repository-wide cap. Compact synthesis can use the configured model input allowance so validated batches normally converge in one grouping request, while every request remains inside the explicit safety ceiling.

One adaptive provider gate schedules independent source batches, capacity-approved concurrent output-space recovery for members of the same source wave, and—after every source batch validates—independent groups within each synthesis level. Complete request-per-minute and token-per-minute capacity metadata bounds concurrent waves by both dimensions. Partial metadata stays sequential; absent metadata starts hosted review at one request and ramps conservatively after successful waves, capped at 32 concurrent calls. Ollama remains serial because its loopback API exposes no portable capacity metadata. A cached qualification is refreshed with the two bounded source-free compatibility contracts (normally two requests, at most four attempts) before a multi-batch run and included in usage and `provider_requests`. Structured validation failures receive sanitized feedback for at most two complete regenerations. If a source or synthesis unit remains too large or invalid, orchestration splits it recursively where semantics allow. Temporary and rate-limit failures use serialized, jittered provider-neutral retries with no more than eight retry cycles or ten cumulative wait minutes for one logical request; ordinary healthy capacity-window waits may repeat across a long low-tier run, while cancellation and the 256-request ceiling remain authoritative. Permanent quota errors return promptly. Schema version 14 adds checked cross-batch gap-resolution audit records; version 13 distinguishes source batches started from batches whose outputs validated and retains provider-request accounting. A completed zero-use result requires every candidate batch to validate; an exhausted or cancelled run preserves accounting and coverage only and discards unsynthesized conclusions. This package does not infer legal applicability, mutate reconciliation or profiles, or write the register.

`internal/technicalreview` applies the same provider-neutral error taxonomy separately to model-directed evidence-search planning and the final evidence judgment. Each operation receives at most four total request attempts inside a ten-minute cumulative wait budget. Reported temporary delays are honored; otherwise transient failures use bounded backoff and rate limits use a conservative one-minute window. Truncated judgment output retries with a larger bounded allowance, and invalid structured output receives a complete replacement attempt under the same trusted validation contract. Permanent quota, intrinsically oversized evidence, cancellation, and exhausted recovery are terminal for that target. Usage and request-attempt accounting from failed retries is retained, validated observations from other targets remain available, and `--require-ai-review` treats any unreviewed requested target as incomplete. Successful observations alone enter the source-free cache.

`internal/inventory` extracts typed signals from dependency declarations, source imports, recognised endpoints, and actual environment-variable access. It aggregates those signals into a versioned component report with scope, evidence type, package version, confidence, and location fields. Detection-signature files can carry the narrow `complyscan:ignore-ai-signals` marker so synthetic definitions do not self-identify as runtime components.

`internal/ownership` validates positive repository-relative gitignore-style patterns and compiles them into a deterministic resolver. A rule with one system assigns dedicated code; one rule naming several systems explicitly shares code. Overlapping matching rules with different owner sets conflict. Paths matching no rule remain unassigned. Ownership is repository structure, not legal applicability, and every referenced system ID must exist in the profile.

`internal/reconciliation` consumes the versioned applicability-to-objective mapping from `internal/framework`; it contains no objective-ID mapping table of its own. For legislation, it screens each technical objective from declared scope, possible high-risk classification, human applicability decision, AI activities, and deployment model. For a selected voluntary framework, relevant objectives remain `recommended-practice` and are never relabelled legal requirements. It then combines that status with the independently produced objective evidence and component inventory. Each evidence reference is resolved through `internal/ownership` before it can be attached to a system. Results explicitly distinguish likely requirements and recommendations with candidate evidence, their corresponding non-detections, unclear applicability, configuration/evidence mismatches, incomplete evaluation, and evidence with conflicting or missing system ownership. With one declared system and no rules, legacy association remains available but is explicitly labelled `single-system-inference`; configuring any rule disables that fallback. With zero or multiple systems, unresolved ownership is never guessed.

`internal/policy` is the narrow bridge from evidence mapping to CI enforcement. It emits `AI-CTRL-001` only when the system profile has a named human reviewer, reconciliation marks an objective `likely-required`, and the deterministic mapping is `requirement-without-detected-evidence`. Draft or incomplete profiles, voluntary recommendations, context-dependent mappings, and model conclusions cannot create a blocking issue. The finding explicitly remains a bounded technical-evidence gap rather than a breach or certification decision.

`internal/rules` owns the severity and finding models plus the deterministic rule interface. Rules receive a read-only repository snapshot. During ordinary scans every rule sees the full snapshot. During `--changed-since` scans, file-local rules receive only committed, staged, unstaged, and untracked changed files; rules implementing `RepositoryWideRule` retain the full snapshot. The documentation and risk-evidence checks use that interface so a small pull request cannot bypass repository-level governance.

The composite GitHub Action always invokes the unified scan but defaults its first-class `ai-review` input to `none`, which explicitly forces deterministic-only operation independently of repository intent or private machine trust. `ai-review: configured` or a provider value is the one-run CI consent surface; `require-ai-review` alone cannot activate a model. Its default `scope: auto` derives the base SHA only for `pull_request` events and change-scopes file-local findings and model context there while repository-wide governance gates keep the full local snapshot; ordinary non-PR events use full scope. An absent or unavailable normal pull-request base is an operational error rather than a privacy-widening full-scan fallback. Change-scoped `pull_request_target` runs are refused because their default checkout cannot represent PR changes safely; use `pull_request` for change scanning, or consciously select a full base-only scan. The Action publishes available SARIF independently, appends the concise Markdown report to the job summary by default, and exposes Markdown and JSON report paths without automatically uploading the raw JSON. Advisory AI observations cannot change deterministic threshold enforcement.

For configured `scan --changed-since` runs, `internal/repositoryanalysis` derives a separate model boundary after local scanning. It retains every changed model-eligible file and adds no more than eight unchanged files connected within two locally indexed graph hops. That scoped in-memory repository—not the complete discovery snapshot—is passed to repository analysis, confirmed-use context binding, technical-investigation construction, eligible-file manifests, and model-directed follow-up. Targeted batching exhausts structural candidates only inside this changed-plus-connected set. Only selected files inside a confirmed use's saved paths enter that use's submitted-file list; a use with no file in the boundary receives no direct model context. Coverage records both the complete locally checked repository and the changed-plus-connected model scope. The separate deterministic per-use fact pass still uses the complete discovered repository, so its facts remain labelled `full-repository` while model facts from this run are labelled `changed-plus-connected`.

`internal/governance` renders AI-system and risk-assessment scaffolds from structured inventory evidence. Generators preserve discovery warnings, label documents as drafts, require human completion, and protect existing documents unless overwrite is explicit.

`internal/baseline` stores deterministic finding identities—including confirmed technical-gap identities—without source evidence. Configured suppressions require a review reason; both mechanisms are applied before reporting and exit-code evaluation. Baselining accepts known work for delta enforcement but does not resolve it or establish compliance.

`internal/report` constructs a schema-version 14 evidence bundle with scan identity, UTC timestamp, tool build, explicit scope, ownership rules and resolution, raw technical AI inventory, an `ai_use_inventory` overlay, per-confirmed-use `ai_use_mappings`, repository analysis, an explicit `repository_analysis_run` lifecycle, and a `frameworks` array. Version 14 adds checked `resolved_evidence_gaps`; version 13 added `source_batches_started` and `provider_requests`, with `source_batches_completed` counting validated source results. Version 12 added exact `member_observation_ids`, version 11 added completed/total source-batch counters, version 10 added repository facts and role candidates, and version 9 added direct confirmed-use observation bindings. The AI-use overlay keeps confirmed, draft, retired, model-suggested, and ungrouped technical observations distinct and never changes the register. Facts, role candidates, and organisation-only unknowns cannot create setup tasks or change profiles, manifests, mappings, applicability, deterministic statuses, or CI gates. JSON remains the exhaustive evidence record and future dashboard contract; Markdown remains a capped developer decision view and SARIF remains a separate source-location integration. The model contributes structured technical judgments and checked citations, while local report code deterministically derives completion status, safeguard counts, action order, workflow/component presentation, and explanatory text. Integrations must consume JSON rather than scraping Markdown.

`internal/reviewcontext` first derives a repository view for each declared system from assigned and intentionally shared paths. It rebuilds the graph inside that view, preserves connected context for owned deterministic candidates, and creates one wider bounded search target for each likely-required system objective without a candidate. Conflicting and unassigned paths never enter these views. The extended search ranks eligible owned files using the versioned pack terms, includes up to six excerpts and a bounded path manifest, and records eligible/matching-file coverage. Model-directed follow-up is restricted to the same in-memory allowed-path set. Its synthetic fingerprint binds the system ID and exact bounded repository context.

`internal/technicalreview` orchestrates one-target evidence-investigation requests, live progress, and source-context-free reuse. Its OS user-cache key binds the provider, model tag, prompt version, technical-pack identity/digest, objective, evidence fingerprint, and a SHA-256 digest of the complete bounded input. Cached observations are validated against their binding, conclusion, assurance, grounded evidence claims, and size limits, then written atomically with user-only file permissions. Submitted source-context records are not stored; bounded redacted model rationales and evidence summaries may still describe repository details.

`internal/repositoryanalysis` separately caches a completed repository-level result outside the repository as `repository-analysis-v6.json`. Cache schema/file version 6 with context version 11 binds prompt version 15, the available qualified model-artifact digest, sparse source extraction, provider-neutral validation feedback, compact grouping with checked cross-batch gap resolution, untruncated local evidence reattachment, trusted observation membership, locally derived candidate IDs, the exhaustive queue, and the larger adaptive hosted evidence packages in addition to the provider endpoint, model, token budget, active review scope, framework evidence, systems, ownership, and confirmed-use contexts. Entries contain the validated advisory result and input digests but no submitted source excerpt, raw manifest, or credential. Only completed synthesis is cached; interrupted batches are not resumed. Per-objective technical observations use `technical-review-v3.json` and bind the same available artifact digest.

`internal/providers` defines the optional review boundary:

```go
type Provider interface {
    Review(ctx context.Context, request ReviewRequest) (ReviewResult, error)
}
```

The provider boundary implements Ollama, native BYOK OpenAI/Anthropic/Gemini adapters, and one reusable OpenAI-compatible adapter used by xAI, Groq, Mistral, OpenRouter, and custom HTTPS services. Repository analysis receives redacted relevant source or trusted subsystem summaries plus typed confirmed-use contexts and returns schema-constrained AI-use suggestions, per-use positive facts, objective observations, unmapped activity, and citations. Anthropic and Gemini receive non-mutating wire-schema copies normalized to their documented structured-output subsets; the complete original schema remains authoritative for trusted local validation. Provider-neutral metadata and error parsing expose request/token capacity, reset intervals, retry delays, transient conditions, and permanent quota exhaustion where a service reports them. Trusted validation rejects unknown objectives/systems/confirmed-use IDs, unknown fact fields or values, fuzzy fact bindings, duplicate fields or use/objective/system observations, unrequested combinations, citations outside the discovered file index or line range, and direct-use citations outside that use's submitted files. Finding review receives visible, unsuppressed, bounded deterministic records. Technical investigation receives existing objective candidates or wider missing-evidence targets plus bounded context. For an uncached target, a planning call may request at most three literal searches over already eligible repository files; trusted `internal/reviewcontext` code returns at most three bounded excerpts before the sole final decision call. Plans never become shell commands, filesystem paths, regular expressions, or additional model rounds. Ollama uses a validated loopback `/api/chat` endpoint with proxies disabled. Native providers use fixed official HTTPS endpoints; compatible presets use documented HTTPS bases; custom providers require a credential-free absolute HTTPS base. All remote clients refuse redirects, may use an operator-configured HTTPS proxy, and read a key value only from the configured environment-variable name. Input and output are redacted and bounded; code and comments are labelled untrusted; and each call has a timeout and response-size limit. Model outputs cannot alter deterministic results, objective status, profiles, the AI-use register, legal applicability, runtime verification, or exit status.

Raw repository source exists only in configured model requests and is never copied into the Markdown or JSON evidence bundle. Reports retain locations and model summaries. With Ollama source remains on the local model boundary; with BYOK it leaves the machine under the selected provider account. A future dashboard will receive the local JSON bundle by explicit connection. `internal/verification` stores reusable recipes from configuration but executes them only when a scan explicitly uses `--verify`; ad-hoc CLI recipes remain available separately. The setup wizard detects only command families and manifest/test-file evidence, never treats repository script text as a command, and requires the user to confirm the exact executable, separate arguments, objective numbers, and system. Each later recipe runs without a shell in a preloaded, network-disabled Docker or Podman image, mounts the repository read-only, applies resource and privilege limits, and records bounded redacted output against user-declared objective and system IDs. `internal/reconciliation` adds a separate test assurance without altering requirement, deterministic evidence, or mapping status. Runtime telemetry, automatic test generation, automatic objective attribution, and legal acceptance remain future layers.

`internal/framework` also owns the source-free technical-evidence benchmark model. A strict versioned manifest labels complete objective candidates, anchors, reachability, required and forbidden relationships, and language coverage for repository-shaped cases. The maintainer runner discovers each labelled repository through the production discovery path, evaluates the embedded pack, emits text or JSON metrics, and fails only against explicit acceptance thresholds. CI runs this independently from the optional live Ollama gate; deterministic graph quality and model quality remain separate measurements.

`internal/profiledraft` owns both the production setup-context selector and its labelled model-quality benchmark. The benchmark passes repository-shaped fixtures through production discovery and inventory, then scores controlled-field precision and recall separately from forbidden claims and invalid or label-inconsistent evidence references. A documentation-only hard negative tests whether terminology is mistaken for implementation. Offline tests verify the evaluator; the maintainer harness invokes a real local model and records time, token, and resource measurements. It is a regression gate for editable suggestions, not a legal assessment or a substitute for human confirmation.

ComplyScan Cloud remains a reserved type only. Any additional remote provider must add an explicit disclosure and consent boundary, use a fixed audited endpoint or an equally strong destination policy, preserve secret redaction, minimise source disclosure, keep credentials out of repository configuration, and keep model observations separate from legal conclusions.
