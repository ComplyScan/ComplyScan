## Intended purpose

ComplyScan is an offline-capable developer CLI that identifies technical signals and missing repository evidence relevant to AI compliance engineering. It helps developers find items that require human review; it does not determine legal compliance, assign a legally binding risk classification, or replace qualified legal and compliance review. Model-free scanning remains available. Development setup recommends a small native BYOK cloud shortlist for advisory review and retains local Ollama and other compatible providers as explicit experimental paths for already-sanitised deterministic findings and bounded connected technical-objective context.

## Current system boundary

The current ComplyScan version consists of:

- bounded local repository discovery and file classification;
- optional bounded repository review that records positive code-visible facts with checked citations;
- identity-bound private machine trust, stored outside the repository, for automatic use of a configured provider on later scans;
- automatic source-free model compatibility qualification with a private expiring cache;
- private, source-free guided-setup recovery checkpoints with final human review before repository configuration is saved;
- typed dependency, import, endpoint, and environment signal extraction;
- deterministic, human-authored pattern and evidence rules backed by a labelled evaluation corpus;
- stable finding fingerprints, reasoned suppressions, and baselines;
- terminal, JSON, SARIF, and structured component-inventory reporting;
- reviewable AI-system and risk-assessment document generators;
- optional Git changed-file scope that preserves repository-wide governance checks;
- optional Ollama, native OpenAI/Anthropic/Gemini, and OpenAI-compatible hosted providers that generate normalized advisory observations for existing findings and technical-objective candidates, using provider-specific wire-schema copies while preserving complete trusted local validation;
- an optional container-only execution verifier that runs an explicitly supplied command against a read-only repository mount with networking disabled and attaches the bounded result to declared objective IDs;
- validated, version-controlled multi-system profiles with provisional EU AI Act scope screening and attributable human applicability decisions;
- validated, version-controlled repository path ownership with explicit shared, conflicting, unassigned, and single-system-inferred evidence states;
- explicit configured AI activities covering inference, training, fine-tuning, evaluation, automated decisions, agent tool use, synthetic-content generation, and unknown context;
- deterministic, versioned EU AI Act and NIST AI RMF technical packs with code-only objectives and no documentary or control-level compliance assessment;
- canonical technical controls that reuse one repository signal across source-specific objectives while preserving separate citations, applicability, and legal nature;
- deterministic reconciliation between screened EU technical requirements or voluntary NIST recommendations and independently discovered repository evidence, including visible gaps, mismatches, and unresolved system ownership;
- a human-owned AI-use register with stable identifiers, guided setup and editing, deterministic per-use requirement mapping, and optional use-bound advisory model observations;
- a language-neutral repository graph with a Go indexer for symbols, imports, calls, routes, configuration, tests, and conservative reachability;
- automatic local Markdown reports and versioned JSON evidence bundles; and
- a verified release installer and guided setup orchestrator that can provision a separately distributed Ollama runtime and user-selected model after explicit confirmation; and
- an optional GitHub Action that builds the CLI and can upload SARIF metadata to GitHub code scanning.

Interactive setup establishes the privacy boundary before repository context can reach a model; Ollama installation or model pulls require separate confirmation. Standard cloud setup contains only OpenAI, Anthropic, and Gemini with two exact quality-oriented candidates each. Ordinary setup does not send repository source or ask the developer for profile classifications. Every standard `complyscan scan` runs the local deterministic layer, records positive code-visible facts as evidence-backed observations, and requires the configured advisory model layer to complete; business, jurisdictional, operational, and legal unknowns remain report-only unless a compliance owner explicitly uses the advanced profile workflow. When a provider was selected after disclosure, setup records repository intent as `ai.review-on-scan: true` and private machine trust keyed to provider, endpoint, model, and credential environment-variable name. Automatic review requires both. A clone, changed identity, or ephemeral runner fails before discovery with actionable approval guidance; explicit provider/model/endpoint/refresh/deep/review options are one-run consent. `complyscan scan --deterministic-only` is the explicit no-model workflow, while `--require-ai-review` remains a compatibility and CI completeness flag without granting consent. Before source is sent, automatic qualification runs both finding-binding and repository-shaped synthetic contracts, normally in two requests with four total requests available for typed temporary retries. It binds qualification contract version 3 and every model prompt contract, including repository-analysis prompt version 20 and setup-draft prompt version 9. Permanent quota, request-size, cancellation, and contract failures stop immediately, with request/token accounting retained. Qualification cache schema 5 is stored separately as `model-qualification-v5.json`, so an older inference contract is not reused. Ollama remains experimental.

The private automatic-review record is stored beneath the operating system's user-cache directory, not in the repository. It contains canonical repository/configuration paths, a digest of the complete AI destination and context settings, the current `adaptive-provider-pipeline-v6` context contract, and a consent timestamp; it contains no credential value or repository source. That contract includes model-aware 24,000–64,000-token hosted source targets, concurrent source and synthesis requests, the bounded representative no-anchor presence sample, and bounded source retransmission during schema repair or transient retry. Its directory and file permissions are restricted to the user, unsafe links and non-regular paths are rejected, and changing any fingerprinted setting invalidates the match.

The separate profile-draft prompt-version 4 gate passed its four-case `qwen3.5:9b` experimental corpus on 2026-08-10 with 88.2% precision and recall, zero forbidden claims, and zero ungrounded references. Ordinary setup does not invoke this capability; it is retained for a future dashboard or explicit compliance-owner workflow. The corpus included a documentation-only hard negative and evaluated the final combined deterministic-plus-model draft. Two false positives and two false negatives remain documented in [profile-draft validation](profile-draft-validation.md). This result does not satisfy or replace the pending `qwen3.5:9b` technical-review gate described above.

The technical packs, canonical control mapping, keyword-group evidence matcher, repository graph, activity-sensitive requirement mapping, ownership resolver, reconciliation, per-use deterministic mapping, repository-fact derivation, and retrieval execution remain deterministic in every configuration. The same canonical control can support separate EU and NIST objectives without conflating a legal-readiness result with a voluntary recommendation. With review disabled, no technical-objective context leaves the CLI process. Ollama receives the bounded context through loopback. A BYOK provider receives the same bounded context through its native, preset, or explicitly configured HTTPS endpoint after consent. The raw configuration, complete profile records, and raw AI-use manifest are not sent, but review requests may include a typed subset of declared system facts needed for technical interpretation: system ID and name, owned paths, intended purpose, lifecycle stage, decision impact, and human-oversight category. For active confirmed AI uses, requests may also include a locally derived typed subset: stable human-owned ID, name and description, saved path scope, valid associated system IDs, exact selected files inside that scope, and likely-required or recommended objective contexts. For every declared system, trusted code creates a repository view containing only assigned or intentionally shared paths and rebuilds graph and retrieval context inside it. Candidate review follows an exact evidence fingerprint attributed to that system and framework objective; missing-evidence review searches only that system view. The model may propose one follow-up plan, but trusted deterministic code validates literal terms, searches only eligible allowed paths, and bounds returned excerpts. Cache and returned observations bind the system ID, objective, fingerprint, ownership scope, confirmed-use contexts, repository digest, and prompt/pack/provider identity. Model observations and repository facts cannot change deterministic reconciliation, profiles, or the human-owned register. The pack's `technical-semantic-and-human` verification labels still require human review and never mean that a model established compliance.

## AI Act applicability assessment

Two operating configurations must now be distinguished.

In deterministic-only mode, the working technical assessment remains that ComplyScan automatically executes human-defined rules and does not use model inference to generate findings. The earlier rationale for treating that configuration as traditional deterministic software therefore remains relevant.

In review-enabled mode, the selected model infers technical-evidence strengths, grounded supporting and contradictory claims, missing evidence, confidence, unresolved questions, and suggested actions from deterministic findings or bounded repository context. Trusted code validates cited paths, binds the result, applies semantic guardrails, and derives both assurance and an explicit repository verdict. “Implemented in reviewed code” requires strong, high-confidence cited support with neither contradictory evidence nor a missing objective element; all other combinations produce partial, not-implemented-in-reviewed-code, or cannot-determine outcomes. These are actionable code-review decisions, but they remain separate from legal applicability, deployment state, operational effectiveness, deterministic findings, and CI exit status. This inference-enabled configuration requires its own applicability assessment and maintained model-quality evaluation.

This assessment follows the distinction in Recital 12 and the European Commission's non-binding guidance between AI systems with an inference capability and simpler software that automatically executes human-defined rules. The project's free and open-source distribution may also be relevant to Article 2(12), but it is not the primary basis for this assessment and its exceptions must be considered if the product changes.

References:

- [Regulation (EU) 2024/1689](https://eur-lex.europa.eu/eli/reg/2024/1689/oj/eng)
- [European Commission guidance on the AI-system definition](https://digital-strategy.ec.europa.eu/en/library/commission-publishes-guidelines-ai-system-definition-facilitate-first-ai-acts-rules-application)

The assessment is not a conformity assessment or final legal determination. Applicable privacy, cybersecurity, consumer-protection, intellectual-property, contract, and other obligations remain separate from the AI Act classification.

## Data flows

The CLI loads its active configuration and optional human-owned AI-use register locally and excludes both exact files from repository discovery before inventory, rules, graph construction, or source context can be built. Normally these are `.complyscan.yml` and `.complyscan/ai-uses.yml`; a custom configuration selected with `--config` receives the same treatment. Typed system facts are constructed separately from the loaded configuration for the analysis steps that require them. The register supplies stable local groupings for deterministic per-use mappings and report overlays; an active configured AI layer may additionally receive only the bounded typed confirmed-use context described below, never the raw manifest. Other YAML files, including GitHub Actions workflows, retain their ordinary repository-evidence treatment. The CLI reads the remaining eligible repository files into process memory and evaluates them locally. It does not collect telemetry. In deterministic-only mode it uploads no source code. Terminal and JSON findings may contain short, sanitised evidence excerpts. Technical-objective results store fingerprints, repository-relative paths, line numbers, file kinds, matched terms, symbol metadata, imports, relationships, reachability, and unresolved questions rather than source excerpts. Structured inventory evidence describes the detected technical signal rather than copying source lines. Secret-shaped evidence is redacted. Baseline files contain finding identity metadata but no source evidence. Completed scans retain immutable date-and-time-named Markdown and JSON pairs beneath `.complyscan/reports/history/` and refresh `latest.md` and `latest.json`; in-progress AI checkpoints update only the latest snapshots. Same-second scans receive a numeric suffix, while the scan ID remains inside each report. History is not automatically deleted. The complete report directory is excluded from scanning and added to `.gitignore` during initialization. Generated governance documents are written only to the user-selected local path and are protected from accidental overwrite by default.

When `ai.review-on-scan` has matching private machine trust or a one-run provider override supplies explicit consent, ComplyScan prepares targeted repository analysis from the discovered snapshot after finishing the deterministic layer. Local inventory signals, technical-objective matches, production entry points, imports, callers, bounded graph relationships, and confirmed-use paths select one bounded redacted excerpt per structural candidate file. If that selector finds no structural AI anchor, ComplyScan instead selects a bounded representative sample of eligible manifests, likely runtime source, and configuration while de-prioritising tests; this presence review is not proof that AI is absent. Repository-analysis prompt version 20 asks source models for atomic observations with trusted request-local block IDs, exact original lines, nested positive facts, and sparse objective decisions. Source extraction uses low reasoning effort, while cross-file grouping uses medium; adapters translate that intent only to provider-supported controls. Anthropic receives a compact equivalent wire grammar for repeated block and fact variants, while ComplyScan retains and locally validates the complete field/value/block/line contract. The model does not invent candidate IDs; ComplyScan assigns scan-local observation identity after line validation and derives the complete observation evidence union locally. Hosted planning uses a confidently known model context window, configured input ceiling, selected evidence size, and live token capacity to prefer one modest request or roughly two balanced bundles around a 48,000-token target, with a 64,000-token latency ceiling; unknown models and compatible gateways stay conservative. Synthesis assigns every trusted observation exactly once and decides only membership, while local code validates it, derives report-local IDs, and reattaches complete checked records. A completed zero-use result requires every selected batch to validate. Invalid output receives at most one corrective regeneration before smaller splitting. When all source batches validate but grouping fails, the report keeps each observation separately and marks only grouping incomplete; incomplete source reviews preserve provider-request, transfer, timing/retry, and batch coverage but discard unvalidated conclusions. No per-request diagnostic retains prompts, source content, file lists, response bodies, or provider request IDs.

One provider-neutral scheduler controls independent source batches, concurrent output-space recovery for affected members of a completed source wave, and—after every source batch validates—independent groups inside each synthesis level. Raw-source batches use the targeted input boundary; synthesis contains a compact grouping view without raw excerpts or repeated report fields and can use the configured model input allowance, so ordinary repositories need one grouping request rather than a fan-out of summary-compaction calls. A live compatibility check can seed the first wave. A cached compatibility result carries no current capacity, so the first useful source request calibrates the scheduler instead of repeating both synthetic compatibility contracts only for headers. When both request-per-minute and token-per-minute capacity are available, both dimensions bound every initial or recovery wave. Partial capacity remains sequential. Header-free hosted scheduling starts at one request and ramps conservatively after successful waves, up to 32 concurrent calls, reducing after failures. Ollama stays serial because its loopback API supplies no portable request/token capacity metadata. Temporary transport, provider, and rate-limit failures honor reported delays or use jittered exponential fallback through the same gate, with at most eight retry cycles and ten minutes of cumulative wait per logical request; ordinary healthy capacity-window waits may repeat over a longer low-tier run, subject to cancellation and the 256-request ceiling. Permanent quota failures stop promptly.

Scans never mutate `.complyscan/ai-uses.yml`. A configured AI layer places automatically grouped suggestions—or separately retained validated observations when grouping is unavailable—in the schema-version 17 report. Version 17 adds stable developer actions plus exact repository/configuration/framework-pack provenance; version 16 added grouping status and per-attempt input/output/reasoning token counts, while version 15's duration/outcome/retry diagnostics, version 14's gap-resolution audit, and version 13's request accounting remain available. Optional dashboard or `ai-uses` workflows can later create durable cross-run identity without making that work a developer setup requirement.

The deterministic fact pass uses the complete discovered repository even during `--changed-since` and currently preserves runtime provider references inside each AI use's path scope. It does not promote an SDK import, endpoint string, or environment-variable reference to an inference activity. Optional model facts retain the narrower changed-plus-connected coverage when that scope is active, and scoped local-CLI packaging is reported only after positive AI activity is supported. Bounded integration and distribution evidence can produce conditional `possible` provider, downstream-provider, or deployer candidates, but never assign an organisation's statutory role. Contracts, customer relationships, operating regions, actual professional or production use, product control, market placement, and the name or trademark used remain report-only organisation unknowns. They do not become setup questions, profile values, applicability outcomes, per-use mappings, or CI gates.

Per-use mapping is deterministic before any model call. Saved paths filter technical evidence, and associated configured systems provide declared applicability context. Multi-system uses are evaluated separately for every system; missing associations leave legal and other context-dependent rules unresolved, while framework-wide voluntary practices may remain recommendations. A validated direct model verdict is added only to its supplied stable use ID and matching objective/system context, with every checked citation inside that use's submitted files. A directly bound uncertain result may be retained without citations only as “cannot determine.” This permits explicit separate evaluation when confirmed uses share code without allowing the model to invent their identity. A generic observation without that stable use binding still requires citations that identify one unambiguous confirmed use. Uncited definite conclusions, invalid bindings, and out-of-scope citations remain repository-level.

Bounded finding review runs for visible, unsuppressed deterministic issue records up to the configured maximum. Informational AI-inventory detections are already deterministic and do not trigger a model request merely to restate them; an empty issue set makes no finding-review call. The older per-objective technical flow runs only in `bounded-only` mode. Its candidate targets contain graph context and connected excerpts; missing-evidence targets contain deterministic search terms, coverage counts, ranked excerpts, and a bounded eligible-path manifest. Repository code and comments are labelled untrusted, source input is re-redacted, and raw source is not copied into reports. Ollama uses validated loopback without proxies. Native remote adapters use fixed official HTTPS endpoints; compatible presets use documented HTTPS bases; custom compatible providers require an explicit credential-free HTTPS base. Remote clients refuse redirects and may respect an operator-configured HTTPS proxy. Responses must conform to separate JSON schemas; Anthropic and Gemini receive non-mutating schema copies normalized to each supported wire subset, while the complete original schema remains authoritative for trusted local validation. Temporary and rate-limit provider failures are distinguished from permanent quota, authentication, and request-shape failures. Returned text is re-redacted and length-limited.

Successful technical observations are cached outside the repository in the operating system's user-cache directory. Cache entries contain the bounded redacted observation and cryptographic digests, not the submitted source-context records. The model is instructed not to quote code, but its rationale may still describe sensitive repository details. Reuse requires an exact provider, model tag, prompt version, control-pack identity/digest, objective, evidence fingerprint, complete bounded-input digest, and active system/review-scope repository digest match. Entries are binding-validated, size-bounded, symlink-refusing, and atomically written with user-only file permissions. `--refresh-review` bypasses reads, and live validation always uses that flag. A model artifact changed in place without changing its configured tag is not automatically detectable; operators must refresh after such an update.

Completed repository-level analysis has a separate private cache with the same no-submitted-source-context design. Cache schema/file version 8 at `repository-analysis-v8.json`, repository-analysis context version 15, and prompt version 20 validate atomic block-cited observations, adaptive model-aware source sizing, compact response limits, stage-specific reasoning effort, Anthropic wire-grammar compaction with strict local validation, the representative no-anchor presence check, per-request token/timing diagnostics, one bounded repair, grouping, and local checked-evidence reattachment. Identity also binds the provider endpoint, model, available qualified model-artifact digest, active review-scope content, framework evidence, declared profiles, ownership rules, confirmed-use contexts, strategy, and token budget. Only a result with completed or unnecessary grouping is cached; separately retained grouping-incomplete observations remain in that report but are retried on a later scan. Individual source batches cannot yet be resumed.

Optional execution verification invokes a user-selected, already installed Docker or Podman runtime and requires a preloaded image, exact executable/arguments, and declared objective IDs. `complyscan verify setup` locally inspects the configured system, every selected framework's conservative requirement or recommendation mapping, manifests, and test-file names; it names the source for each objective and saves only mappings explicitly selected and finally confirmed by the user. Detected repository scripts are used only to identify a native runner family, not copied into an executable command. The wizard cannot execute or provision anything. Reusable repository recipes remain inert unless a later scan explicitly passes `--verify`; one-off CLI flags are a separate explicit boundary. ComplyScan does not use a shell, pull an image, or enable container networking. It applies a read-only repository mount and root filesystem, drops capabilities, enables no-new-privileges, and bounds processes, memory, CPU, temporary storage, time, and captured output. The selected image and container runtime remain external trust boundaries. A pass adds separately labelled test-evidence assurance to the declared objective and system without changing deterministic evidence or mapping. Bounded redacted result metadata and output may enter configured model context only when both the declared objective and system match that investigation target. Test output may itself contain repository or runtime details. A result cannot prove objective coverage, establish production effectiveness, or change compliance, legal applicability, findings, or failure-threshold status.

Default setup first inspects the repository locally without a model, then asks whether optional AI assistance is permitted. After that boundary is established and the selected model passes compatibility checking, setup may send bounded, best-effort-redacted context to prepare editable suggestions. The user confirms system facts, selects technical mappings, and answers only relevant follow-up questions. Selecting a provider records `ai.review-on-scan: true` as repository intent and a matching private trust record on that machine; the final step offers the same unified scan or saving only. Before setup assistance or a later scan trusts an unseen model with repository context, ComplyScan runs source-free synthetic finding and repository-shaped contracts and requires correctly bound schema-valid responses. Compatibility demonstrates minimum protocol behavior only, not review quality or legal accuracy. Credentials remain in the shell or CI secret store.

When explicitly enabled, the GitHub Action uploads SARIF containing finding messages, repository-relative paths, line numbers, remediation text, and fingerprints. ComplyScan SARIF intentionally omits source excerpts and detected credentials. Its first-class `ai-review` input defaults to `none` and forces deterministic-only operation; AI requires an explicit `configured` or provider value, and `require-ai-review` alone is not consent. Default `scope: auto` uses changed-plus-connected context only for `pull_request`; ordinary non-PR events use full context, while an unavailable normal pull-request base fails rather than silently widening the boundary. Change-scoped `pull_request_target` runs are refused because their default checkout cannot assess the proposed changes safely; use `pull_request` for change scanning, or consciously request a full base-only scan. The Action appends the concise Markdown report to the GitHub job summary by default and exposes local Markdown and JSON report paths, but never uploads the raw JSON bundle automatically. When the AI layer runs, SARIF additionally carries advisory provider/model metadata, verdicts, confidence, rationales, and suggested actions. Those observations do not change the deterministic finding threshold. A BYOK credential must enter the job through a secret-backed environment variable, never an action input.

## Human oversight and expected use

Every finding is a review prompt. Users are expected to:

- inspect the complete system and deployment context;
- confirm or reject technical signals;
- treat every model observation as untrusted advisory input rather than a finding or legal conclusion;
- complete and approve generated governance scaffolds rather than treating them as finished assessments;
- document suppression decisions with reasons;
- avoid treating a clear scan as proof of compliance; and
- obtain qualified review for legal classifications and obligations.

Ordinary guided setup creates a draft report target and deliberately leaves organisation-only facts unknown; it does not ask developers to make legal, market, data, or operational classifications. Code-visible facts are inferred during scanning and remain evidence-backed report observations. The explicit advanced/profile workflow can record declared facts and optional human decisions for a compliance owner, but ComplyScan does not verify their truth or legal sufficiency. Reviewed profiles must be reassessed when the system's purpose, markets, actors, users, affected groups, data, deployment, or decision impact changes.

## Reassessment triggers

This assessment must be reviewed before any model review is promoted from experimental status and again if ComplyScan adds any of the following:

- another remote model-backed provider, a configurable remote destination, or a material provider API change;
- learned, adaptive, probabilistic, or model-derived logic that creates, removes, re-severities, suppresses, or gates deterministic findings;
- remote, over-budget, mis-scoped, or non-consensual source-file or repository-content disclosure to a review provider;
- hosted scanning, complete or persistent source-code upload, telemetry, or persistent scan storage;
- automated legal conclusions or risk classifications presented without meaningful human review;
- decisions or recommendations used in employment, education, credit, essential services, law enforcement, migration, biometrics, safety components, or other regulated contexts; or
- a material change to intended purpose, users, affected persons, distribution, or commercial model.

The review must record the system definition analysis, operator roles, risk classification, data flows, transparency duties, human oversight, testing evidence, and any required conformity or registration steps.
